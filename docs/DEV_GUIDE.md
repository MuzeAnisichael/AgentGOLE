# GoleKit 开发指导

本文规定**怎么做**：工程约定、版本流程、multi-agent 分工、测试纪律、Git 规范，以及与审核方的协作循环。**做什么**由 `docs/tasks/v0.X.md` 和 `docs/SPEC.md` 规定。

---

## 1. 工程约定

### 1.1 语言与工具

- Python ≥ 3.11；用 uv 管理环境与依赖。
- ruff 负责 lint 和格式化（line-length 100）；pyright 默认用 basic 模式，`protocols/`、`kernel/` 用 strict 模式。
- 测试用 pytest + pytest-asyncio；`live` 标记的测试默认不运行。
- `make check` = `ruff format --check` + `ruff check` + `pyright` + `pytest`（不含 live）。本地和 CI 跑的是同一条命令。

### 1.2 代码结构

- **异步优先**：所有 I/O 都写成 async。同步 API 只在 `_sync.py` 里统一包装，其他地方禁止直接调用 `asyncio.run`。
- **数据类型**：跨模块传递的数据统一用 pydantic v2 模型（`Message`、`ToolCall`、`ToolSpec`、`Usage`、`Event` 等），集中定义在 `protocols/types.py`。
- **协议**：组件接口用 `typing.Protocol` 定义，放在 `protocols/`；只在确实需要做运行时检查时才加 `runtime_checkable`。
- **公共 API**：只从 `golekit/__init__.py` 导出，并用 `__all__` 显式列出。其余模块都算内部实现，可以随时调整。
- **可选依赖**：只能在函数内部 import；捕获 `ImportError` 后，抛出带安装命令的 `MissingDependencyError`。
- **配置优先级**：显式参数 > 环境变量 > `gole.yaml` > 默认值。密钥只从环境变量读取，绝不写进日志或报错信息。
- **错误**：异常统一定义在 `errors.py`，基类为 `GoleError`。面向用户的报错要告诉对方下一步怎么做，例如缺少的环境变量名、该装的 extra。
- **日志**：用 `logging.getLogger("golekit.<module>")`。库代码不 `print`（CLI 和 `verbose` 输出除外），也不配置 root logger。
- **禁止**：
  - import 时发起网络请求或读写文件；
  - 全局可变单例（注册表除外）；
  - monkeypatch 第三方库；
  - 空的抽象层（只有一个实现、也没有任务书要求的接口，就不要抽象）。

### 1.3 注释与文档

- 公共符号必须有 docstring（Google 风格，英文），最好带一行用法示例。
- 只在「为什么这么做」不明显时写注释；不写复述代码的注释。
- 不新增 README 以外的说明文档，文档由审核方维护。

## 2. 版本开发流程

| 阶段 | 谁做 | 产出 | 结束条件 |
| --- | --- | --- | --- |
| P0 计划与接口 | Lead | 任务卡；共享类型、协议、存根；`FakeModel` 等公共测试工具 | 接口已提交，任务书中的公共签名全部存在（可以是存根） |
| P1 并行实现 | Builder ×1–3 | 各自目录下的实现和单元测试 | 每张任务卡的「完成定义」都满足 |
| P2 集成 | Lead | 公共 API 组装、`__init__` 导出、示例、CLI | `make check` 通过 |
| P3 评审（可选） | Reviewer | 只读的问题清单 | Lead 处理完所有必须修改的问题 |
| P4 验收与报告 | Lead | 验收结果、`reports/v0.X-report.md` | 报告写完，停止 |

接口在 P0 之后视为冻结。P1 期间如果需要改接口，必须走 §3.6 的流程。

## 3. Multi-agent 使用指导

并行的目的是**缩短耗时、隔离上下文**，不是增加验证轮次。Agent 越多，协调成本越高，所以只在收益明显时才拆。

### 3.1 角色

| 角色 | 数量 | 职责 | 不做什么 |
| --- | --- | --- | --- |
| Lead（主 Agent） | 1 | 读任务书；拆任务卡；编写共享接口和类型；独占共享文件；集成；跑 `make check`；执行验收；写报告 | 不把集成、修复失败测试、验收、写报告交给别的 Agent |
| Builder | 同时 1–3 个 | 按任务卡在自己负责的目录里实现，并写对应的单元测试 | 不改负责范围以外的文件；不跑全量测试；不擅自改接口 |
| Reviewer | 0–1 个，集成后 | 只读审查：对照任务书、SPEC、依赖规则和范围纪律，输出问题清单 | 不改代码；不跑测试；不提 ruff 已经管住的风格问题 |

### 3.2 什么时候并行

**适合并行**：
- 接口已经提交；
- 任务之间只通过 `protocols/` 交互；
- 各自改的文件互不重叠；
- 单张任务卡预计改动超过 150 行左右。

**不要并行**：
- 接口还没定；
- 修一个失败的测试，或排查一个 bug；
- 改动不到 150 行左右，或几项改动集中在同一个文件；
- 验收和写报告。

同时运行的 Builder 最多 3 个。

### 3.3 共享文件

以下文件只有 Lead 能改；Builder 需要改时，在回报里提出：

`pyproject.toml`、`Makefile`、`src/golekit/__init__.py`、`src/golekit/errors.py`、`src/golekit/protocols/**`、`tests/conftest.py`、`CHANGELOG.md`、CI 配置。

如果环境支持隔离工作区（git worktree 或独立分支），每个 Builder 用一个；不支持的话，就靠文件归属来避免冲突。

### 3.4 任务卡模板（Lead 发给 Builder）

```text
任务卡 T{n}：{标题}
目标：{一句话}
负责文件（只能改这些）：{目录或文件列表}
依赖的接口（只读）：{protocols/ 中的文件与符号}
要实现：
  - {公共符号与签名，从任务书原样复制}
  - {行为要点，3–6 条}
必须覆盖的测试（不超过 8 个）：{逐条列出要验证的行为}
完成定义：定向测试通过 + ruff check {负责目录} 无报错 + 按 §3.5 格式回报
不要做：{明确排除的内容}
需要读的 SPEC 章节：{只列相关小节}
```

### 3.5 Builder 回报格式（不超过 10 行）

```text
T{n}：完成 / 部分完成 / 受阻
改动文件：...
新增或修改的公共符号：...
测试：N 个，全部通过（命令：uv run pytest tests/unit/test_x.py -q）
对接口的疑问或建议：...（没有就写「无」）
```

只回传摘要，不回传日志，也不回传大段代码。

### 3.6 接口变更与冲突

- Builder 发现接口不够用时，停下这部分工作并回报 Lead。不要自己绕开接口，也不要改 `protocols/`。
- Lead 统一修改接口，通知所有受影响的 Builder，并在报告的「偏差与决策」里记录。
- 合并顺序跟着依赖走：类型与协议 → 内核 → 组件（models、tools、memory 等）→ 范式 → 公共 API 组装。

### 3.7 上下文卫生

- 给 Builder 的上下文只有：任务卡、相关接口文件、SPEC 中相关的小节。不让 Builder 通读仓库或整份 SPEC。
- Reviewer 只看本版本的 diff、任务书和依赖规则。
- Lead 不重复阅读已经读过且没有改动的文件。

### 3.8 Reviewer 输出格式

```text
必须修改（影响正确性、违反任务书或依赖规则）：
  1. {文件:行} {问题} → {建议}
建议修改（可以留到下一版）：
  1. ...
```

问题清单最多 15 条，按严重程度排序。Lead 只处理「必须修改」，「建议修改」原样写进报告。

## 4. 测试与验证纪律

原则：测试是为了证明任务书里的行为成立，而不是反复确认已经确认过的事。每多写一个测试、多跑一次测试，都要能回答「它能发现什么新问题」。

### 4.1 写什么

- 只测公共行为，以及任务书点名的边界情况。
- 每修一个 bug，补一个回归测试。
- 每张任务卡一般 3–8 个测试；超过 10 个，要在回报里说明理由。
- Agent 的行为一律用 `FakeModel` 测试，不联网；HTTP 层用 `httpx.MockTransport`。

**不写**：
- 第三方库或标准库的行为；
- 平凡测试（pydantic 字段默认值、简单的 getter）；
- 私有函数的实现细节；
- 整段 prompt 的快照测试；
- 超过 5 组参数的参数化（除非任务书列出了这些情况）；
- 性能和压力测试（除非任务书要求）。

**例外：降级解析的语料测试。** 模型输出的修复和解析（`_json.py`、`paradigms/` 里的协议解析）是核心卖点，它的测试用真实的坏输出驱动。语料放在 `tests/corpus/`，每条样本一个文件，由一个参数化测试跑完全部样本；样本数量不受上面「每卡 3–8 个」和「参数化不超过 5 组」的限制。样本必须来自基准、live 验收或用户报告里真实出现过的模型输出，不要凭空编造。

### 4.2 什么时候跑、跑多少

| 时机 | 跑什么 | 次数 |
| --- | --- | --- |
| Builder 开发中 | 正在改的那一个测试文件（`-x -q --tb=short`） | 按需，但代码没改就不重跑 |
| Builder 交付前 | `ruff check {负责目录}` + 自己负责的测试文件 | 1 次 |
| Lead 集成后 | `make check` | 1 次；失败就修复，用 `pytest --lf` 只重跑失败项，最后再跑 1 次 `make check` |
| 验收 | 任务书列出的验收命令和示例 | 每项 1 次 |

- 代码没有改动，就不重跑任何测试。只改了文档、注释或报告，不跑测试。
- 不写临时验证脚本，也不用 `python -c` 去重复已有测试覆盖过的检查。
- 失败时只看第一个失败（`-x`），不要反复翻看长日志。
- 真实模型测试（`-m live`）只在验收阶段跑，每个环境跑一次。环境不可用时，直接标记「待人工验证」，不要模拟，也不要循环重试。
- v0.x 不设覆盖率门槛，不为凑覆盖率补测试。
- `ruff format` 在提交前运行一次即可，不要反复格式化。

### 4.3 失败处理与时间盒

- 同一个失败最多尝试修复 3 次。仍然失败时，停下这一项，在报告的「已知问题」里写明现象、试过的方案和怀疑的原因，然后继续其他任务。
- 疑似偶发失败时，不要循环重跑。先找出不确定性的来源（时间、随机数、并发、网络）并消除；实在消除不了，就标记 `xfail` 并在报告中说明。
- `make check` 通过、验收完成，就结束这个版本。

## 5. Git 规范

- 分支：`v0.X`，从上一版审核通过后的提交切出。
- 提交：每张任务卡至少一个提交。
  - 标题用 Conventional Commits，末尾加任务编号，例如 `feat(memory): add rolling summary memory [T2]`。
  - 正文用 2–5 行列出要点：做了什么、有哪些取舍。
  - 遗留修复、评审修改和返工，每条一个提交，编号分别用 `[R1]`、`[RV3]`、`[RW2]` 的形式；不要把多条修改合并进一个「集成修复」提交。
- `CHANGELOG.md`：每版在 `## [Unreleased]` 下按 Added / Changed / Fixed 写条目，写到功能级：新增的公共 API、CLI 命令、行为变化、已知限制，每条一行；破坏性变更以 **BREAKING** 开头。
- 不打 tag、不合并到 main、不改 `docs/`，这些由项目负责人和审核方处理。

## 6. 与审核方的协作循环

1. 项目负责人把 `docs/tasks/v0.X.md` 交给你，你按 AGENTS.md 的流程完成这个版本。
2. 你把报告写进 `reports/v0.X-report.md`，然后停止。
3. 项目负责人把报告转给审核方。审核方回复以下两种结果之一：
   - **通过**：附带下一版任务书 `docs/tasks/v0.(X+1).md`，以及需要同步的文档更新。
   - **返工**：附带返工清单。你只处理清单里的项目，并在原报告末尾追加「返工记录」一节，不要重写整份报告。
4. 报告是审核方了解代码的主要途径。仓库推到 GitHub 后，审核方也可能直接读代码，但报告里仍要写清公共接口签名和各项决策。
