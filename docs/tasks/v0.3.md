### 2.2 本版新增的公共 API

```python
import agentgole as gole
from agentgole import approval, paradigms

# —— 范式 ——
gole.Agent(paradigm="direct" | "auto" | "react" | "plan" | "reflect" | Paradigm)
paradigms.Direct()
paradigms.PlanExecute(planner=None, executor=None, max_replans=2)
paradigms.Reflect(critic=None, rounds=2, criteria=None)
paradigms.Auto(); paradigms.React()                 # v0.1 已有，随子模块一起公开
# planner / executor / critic：模型 spec、别名（如 "smart"）、Model 或 ModelClient；None 表示用 Agent 的模型

# —— 审批 ——
@gole.tool(confirm=True)                            # 执行前需要确认
gole.Agent(approval=None)                           # None | approval.Console() | approval.Callback(fn)
approval.Console()                                  # 终端 y/N
approval.Callback(fn)                               # fn(tool: str, args: dict) -> bool，同步或异步

# —— 内置工具 ——
gole.Agent(tools=["web_search", "web_fetch", "python", "shell"])     # 字符串引用使用默认配置
gole.tools.web_search(provider=None, max_results=5)                   # provider: "duckduckgo" | "tavily"
gole.tools.web_fetch(allow_private=False)
gole.tools.python(timeout=10, confirm=True)
gole.tools.shell(cwd=None, timeout=30, confirm=True)
gole.tools.files(root, write=False)                 # 返回工具列表：read_file、list_dir；write=True 时加 write_file
# tools= 的元素可以是工具列表，展开一层。字符串 "files" 抛 ConfigError，提示改用 gole.tools.files(root=...)

# —— 约束解码 ——
gole.Model(spec, ..., constrained=None)             # None：按 provider 默认；True / False：强制开或关
model.capabilities.json_schema                      # Capabilities 新增字段
```

`gole doctor` 的每个聊天模型多输出一项「约束解码: 支持 / 不支持」。

## 3. 关键设计约束

### 3.1 类型与协议扩展（P0，Lead）

- `CallModel` 新增三个字段：
  - `model: ModelClient | None = None`：本次调用使用的模型，`None` 表示 `ctx.model`；
  - `visible: bool = True`：`False` 表示这次调用的文本是内部中间产物，不发 `token` 事件；
  - `response_schema: dict | None = None`：希望回复满足的 JSON Schema，由引擎按 §3.5 决定是否交给后端。
- 引擎不再按范式的类型决定是否发 token，只看 `visible`、工具模式和 D-301。自定义范式的调用默认可见；多次调用的范式自己把中间调用标成 `visible=False`。
- `Capabilities` 新增 `json_schema: bool = False`。
- 事件新增 `approval_required`，字段为 `tool` 和 `args`（与 SPEC §8.1 一致）。
- 新协议 `Approver`：`async def approve(tool: str, args: dict[str, Any]) -> bool`。
- `Tool` 协议不变。工具对象上可选的 `confirm: bool` 属性表示需要确认，缺省视为 `False`。
- 范式的可选钩子 `bind(model: ModelClient) -> None`：Agent 构造时，如果范式对象有这个方法，就调用一次，传入 Agent 的模型。
- 新建共享模块 `src/agentgole/_html.py`，把 `knowledge/loaders.py` 里的 HTML 可见文本提取移进去，知识库加载器和 `web_fetch` 共用（R8 的一部分）。本版新增代码不得再让组件互相导入（D-212）。

### 3.2 范式（`paradigms/`）

三个新范式都只通过返回 Action 工作，不直接调用模型（D-303）。需要工具循环的地方，内部委托给 `Auto`，这样原生、prompt、约束解码三种工具调用方式都自动可用。

- **`Direct`**：一次 `CallModel(use_tools=False)`，然后 `Finish`。Agent 构造时如果同时注册了工具、使用了 `write="tool"` 的记忆，或显式指定了 `knowledge_mode="tool"`，抛 `ConfigError`；`knowledge_mode="auto"` 在 `direct` 下解析为 `context`。
- **`PlanExecute`**（字符串 `"plan"`）：
  1. **规划**：用 planner 发一次不可见调用，要求返回 JSON 字符串数组，每个元素是一个步骤。通过 `_json.OutputSchema(list[str])` 解析；超过 8 步时只保留前 8 步。解析失败时带错误信息重试 1 次，仍失败则把整个任务当成唯一的一步，并通过 `ctx.report_error` 上报。
  2. **执行**：逐步执行。每一步新建子对话：开头的系统消息保持不变，再加一条 user 消息，包含总任务、已完成步骤及其结果、当前步骤。委托 `Auto` 循环直到它给出 `Finish`，其文本就是这一步的结果。带入后续步骤时，每个结果最多保留 2000 字符。执行阶段的调用都不可见。
  3. **检查**：全部步骤完成后，如果已重规划次数小于 `max_replans`，用 planner 发一次不可见调用，返回 `{"done": bool, "plan": [...]}`。`done` 为假且 `plan` 非空时，计一次重规划，继续执行新步骤，之前的结果保留。解析失败视为 `done`。`max_replans=0` 时跳过检查。
  4. **汇总**：用 planner 发一次可见、不带工具的调用，根据总任务和各步结果写出最终回答，然后 `Finish`。
  - 当前计划保存在 `state.scratch["plan"]`；规划和重规划那一步的 `step` 事件，`thought` 字段带上计划文本。
- **`Reflect`**（字符串 `"reflect"`）：
  1. **起草**：委托 `Auto` 循环得到初稿（可以使用工具）。`rounds == 0` 时初稿可见，完成后直接 `Finish`，不评审；否则初稿不可见。
  2. **评审**：用 critic 发一次不可见调用，输入为用户问题、当前稿和评审标准，返回 `{"pass": bool, "feedback": str}`。`criteria` 缺省为「回答准确、完整、切题」。解析失败视为通过，并上报。
  3. 通过：以当前稿 `Finish`。
  4. 未通过：用 Agent 的模型发一次不带工具的修订调用，输入为当前稿和评审意见。第 `rounds` 次修订是最后一次，标为可见，完成后直接 `Finish`，不再评审；之前的修订不可见，完成后回到第 2 步。
- **模型解析**：`planner`、`executor`、`critic` 是字符串时，在构造时按与 `memory.Summary(model=...)` 相同的方式解析；`None` 时用 `bind` 传入的 Agent 模型。
- **主模型**：`PlanExecute` 指定了 `executor` 时，本次 run 的 `ctx.model` 和工具模式解析都改用它。
- **用量和步数**：所有调用都计入 `result.usage` 和 `max_steps`。步数用尽时照常抛 `MaxStepsError`。
- **流式**：只有汇总调用（plan）和最后一次修订（reflect）逐 token 发出。reflect 提前通过评审时，最终文本在 `Finish` 时一次性补发。两种范式都满足 D-301。
- **结构化输出、记忆、知识库**：行为与 `auto` 相同。`output=` 的校验仍在引擎处理 `Finish` 的位置；`context` 模式的参考资料在开头的系统消息里，子对话自然带上；`tool` 模式的检索工具在执行阶段可用。

### 3.3 审批（`safety/approval.py`，公开为 `gole.approval`）

- `@gole.tool(confirm=True)` 把工具标记为需要确认。
- 调用路径：参数校验 → 发 `approval_required` → `approver.approve(tool, args)` → 执行。参数不合法的调用不触发审批。
- 批准：照常执行。拒绝：不执行，工具结果为错误 `Rejected by the user.`，作为观察返回给模型，run 继续。
- Agent 没有配置 `approval` 时，需要确认的工具一律不执行，错误信息提示给 Agent 传 `approval=`（D-304）。`approval_required` 事件照发。
- `Console`：向 stderr 打印工具名和参数（JSON，超过 500 字符截断），在工作线程里从 stdin 读一行；`y` 或 `yes`（不区分大小写）为批准，其余输入和 EOF 都是拒绝。
- `Callback(fn)`：`fn` 可以是同步或异步函数。`fn` 抛异常时按拒绝处理，并通过 `ctx.report_error` 上报。
- 等待审批的时间计入 run 的 `timeout`。
- `gole chat`：Agent 没有配置 `approval` 时，CLI 为它设置 `Console()`。

### 3.4 内置工具（`tools/`）

工厂函数放在 `agentgole.tools` 命名空间；字符串引用等价于无参调用工厂。所有工具都要在 Windows 和 POSIX 上工作。输出上限沿用 D-103 的 8000 字符。

- **`web_search(query)`**：返回带编号的结果，每条包含标题、链接和摘要。
  - provider 的解析顺序：工厂参数 → 环境变量 `GOLE_SEARCH_PROVIDER` → gole.yaml 的 `tools.web_search.provider` → `duckduckgo`。
  - `duckduckgo`：请求其 HTML 结果页，用标准库 `html.parser` 解析，不需要密钥。
  - `tavily`：调用其搜索 API，密钥取自 `TAVILY_API_KEY`；缺少密钥时在 Agent 构造时抛 `ConfigError`。
  - 网络失败或解析不到结果时，返回工具错误，不中断 run。
- **`web_fetch(url)`**：只接受 http(s)。HTML 用 `_html.py` 提取可见文本，其他 `text/*` 原样返回，非文本类型返回工具错误。超时 20 秒，最多跟随 5 次重定向，最多读取 2 MB。默认拒绝回环、私有和链路本地地址，重定向后的地址同样检查；`allow_private=True` 时放开。
- **`python(code)`**（D-305）：
  - 用当前解释器以隔离模式启动子进程，脚本写进新建的临时目录并以它为工作目录。
  - 环境变量只保留运行解释器必需的几项，任何 `*_API_KEY` 都不传入。
  - 启动时禁用 `socket`，联网会直接报错。
  - 超时（默认 10 秒）后终止整个进程树。
  - 返回 stdout 和 stderr；退出码非零时附上退出码。
  - 默认 `confirm=True`。docstring 里写明这不是安全边界。
- **`shell(command)`**：通过系统 shell 执行，工作目录默认为当前目录，超时默认 30 秒，超时后终止整个进程树。返回 stdout、stderr 和非零退出码。默认 `confirm=True`。
- **`files(root, write=False)`**：
  - `read_file(path)`：UTF-8 读取，非法字节替换。
  - `list_dir(path=".")`：列出名称，目录以 `/` 结尾。
  - `write_file(path, content)`：只有 `write=True` 时才提供；父目录不存在时创建。
  - 路径规则：相对 `root` 解析；解析后的真实路径必须位于 `root` 之内，`..`、绝对路径和指向外部的符号链接都返回工具错误。`root` 不存在或不是目录时，在构造时抛 `ConfigError`。

### 3.5 约束解码（降级第二阶段，D-307）

- **能力**：`Capabilities.json_schema` 的 provider 默认值：`ollama`、`lmstudio`、`vllm`、`openai` 为真；`deepseek`、`dashscope` 和自定义 `base_url` 为假。`gole.Model(..., constrained=True / False)` 强制覆盖。
- **线上格式**：在请求体里加 `response_format={"type": "json_schema", "json_schema": {"name": ..., "schema": ...}}`。只加在不带原生工具的模型调用上；带 `tools` 的请求不加。
- **回退**：后端以 HTTP 400 拒绝该字段时，把这个模型标记为不支持（与原生工具被拒时的降级共用一套机制），发一个可恢复的 `error` 事件，同一次调用去掉该字段后重发。
- **用在三处**：
  1. `output=`：不带原生工具的最终回答调用和纠正调用带上输出类型的 schema。校验和纠正逻辑不变。
  2. prompt 模式的工具循环：`json_schema` 可用时，用受约束的协议代替文本 ReAct。每次回复是一个 JSON 对象，schema 是各工具的 `{"thought": str, "tool": <工具名常量>, "arguments": <该工具的参数 schema>}` 再加上 `{"thought": str, "tool": "final_answer"}` 的 `anyOf`。选了工具就 `CallTool`；选了 `final_answer` 就再发一次可见、不受约束、不带工具的调用生成最终回答。`thought` 写进 `step` 事件。
  3. 范式内部的结构化调用（规划、检查、评审）。
- `json_schema` 不可用时，以上三处都退回 v0.2 的做法：提示词约定格式，加共享的 JSON 修复和带报错重试。文本 ReAct 的行为不变。
- 各后端对 `response_format` 的支持以 live 验收（C11、C12）的实测为准。实测不支持的 provider，把默认值改为假，并写进报告的「偏差与决策」。

### 3.6 工具调用基准（`benchmarks/tool_calling/`，D-308）

- `cases.py`：20 个用例，5 类各 4 个：单工具单参数；多参数与类型（整数、浮点、布尔、枚举、列表）；两步调用（第二次的参数依赖第一次的结果）；不需要工具；工具报错后恢复。工具都是确定性的本地桩函数。每个用例给出判定函数：工具调用序列（名称和参数）符合预期，并且最终回答包含预期内容。
- `run.py --models <spec,...> --modes native,prompt,constrained --out RESULTS.md`：`temperature=0`，每个用例跑一次。模型不支持的模式标为「不支持」，不计入成功率。
- `RESULTS.md`：每个「模型 × 模式」一行，列出成功率、平均模型调用次数、格式重试总数、平均耗时；另附运行日期、模型摘要（digest）和硬件概况。
- R9 的观察项：每个模型另跑一次 `memory="long"` 加知识库的问答，把请求是否成功、回答是否用到了记忆和参考资料记进 `RESULTS.md`。
- 基准脚本纳入 ruff 和 pyright，不纳入 `make check` 的 pytest。判定函数用 `FakeModel` 写 1–2 个单元测试。
- 建议的模型：`ollama/qwen3:8b`、`ollama/qwen3:4b`、`ollama/llama3.2:3b`，以及一个不支持原生工具调用的模型（如 `ollama/gemma3:4b`）。项目负责人可以按本机已有的模型替换，但不少于 3 个。

## 5. 验收标准

| 编号 | 标准 | 方式 |
| --- | --- | --- |
| C1 | `make check` 通过 | 自动 |
| C2 | R1–R7 各有一个回归测试并通过；R1 的测试断言首个 token 在模型流结束前到达 | 单元测试 |
| C3 | `direct`：只发一次模型调用，请求里不带工具；与工具同时使用时抛 `ConfigError` | 单元测试 |
| C4 | `plan`：两步计划（其中一步调用工具）后汇总；检查后重规划一次；`max_replans=0` 时没有检查调用；planner 和 executor 是不同模型时，各自只收到自己的调用；流式下只有汇总的文本以 token 发出 | 单元测试 |
| C5 | `reflect`：首轮通过；修订一次后通过；轮数用尽时返回最后一版且不再评审；critic 是独立模型时只收到评审调用 | 单元测试 |
| C6 | 审批：批准后执行；拒绝后模型收到错误并继续；未配置审批时不执行；每次都发 `approval_required`；`Console` 用 monkeypatch 的输入测试 | 单元测试 |
