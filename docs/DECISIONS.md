## v0.3 任务书（下发：2026-11-25）

| 编号 | 决策 | 理由 | 来源 |
| --- | --- | --- | --- |
| D-301 | 流式 token 的不变量改为：最后一个 `tool_result` 事件之后发出的 token，拼接起来等于 `result.text`；没有工具调用时即全部 token。原生模式下文本增量到达即发，工具调用之前的文本属于中间文本。取代 v0.1 审核 R2 中「拼接全部 token == result.text」的表述 | 原生模式下流结束前无法判断文本后面有没有工具调用，旧不变量迫使整段缓冲，带工具的 Agent 失去流式体验 | v0.2 审核 R1 |
| D-302 | `memory.save` 失败（包括保存阶段触发超时）不使 run 失败：发 `recoverable=True` 的 `error` 事件并记 warning，照常返回 `Result` | 回答已经生成并可能已经流式发出；`Summary` 压缩失败本来就不中断，行为应当一致 | v0.2 审核 R2 |
| D-303 | 范式内部的模型调用一律通过 `CallModel` 交给引擎，新增 `model` 和 `visible` 两个字段；全部计入 `usage` 和 `max_steps`。指定了 `executor` 时，它就是本次 run 的主模型，工具模式按它解析 | 事件、轨迹和用量统计保持完整；工具循环由哪个模型执行，就按哪个模型的能力决定调用方式 | v0.3 任务书 §3.2 |
| D-304 | 需要确认的工具，在没有配置审批方式时拒绝执行，拒绝原因作为工具错误返回给模型；`gole chat` 默认使用终端确认 | 库不应擅自读标准输入，也不能在无人确认时放行危险动作 | v0.3 任务书 §3.3 |
| D-305 | `python` 和 `shell` 两个内置工具默认都需要确认。`python` 的子进程隔离只是尽力而为（独立解释器、清空环境变量、禁用 socket、超时），不是安全边界；Docker 沙箱留到 v0.8 | 在容器沙箱到位之前，模型写的代码能读写用户的文件。SPEC §6.2 原先只写了 `shell` 默认确认，这里从严 | v0.3 任务书 §3.4 |
| D-306 | `web_search` 的搜索提供方可配置，本版内置 `duckduckgo`（默认，无需密钥）和 `tavily`（需要 `TAVILY_API_KEY`） | 默认零配置可用；需要稳定结果时换成有密钥的服务 | v0.3 任务书 §3.4 |
| D-307 | 约束解码统一走 OpenAI 兼容的 `response_format` JSON Schema 字段，只加在不带原生工具的模型调用上。prompt 模式下用它约束「选哪个工具、参数是什么」；最终回答另起一次不受约束的调用生成 | 一种线上格式覆盖 Ollama、vLLM、llama.cpp 和 LM Studio；最终回答不放进 JSON，才能保持流式和文本质量 | v0.3 任务书 §3.5 |
| D-308 | 工具调用基准的脚本和结果放在 `benchmarks/tool_calling/`，结果文件为 `RESULTS.md`；审核方审核后摘录进 SPEC | `docs/` 由审核方维护，开发方不改 | v0.3 任务书 §3.6 |
| D-309 | 上下文长度的最小版提前到 v0.3：长度可配置（`context=`、`GOLE_CONTEXT`、gole.yaml），提示词用量达到 90% 时记 warning 并在 `model_end` 上带 `context_used`，`gole doctor` 显示该值。压缩和 `TokenBudget` 仍在 v0.8。GoleKit 不修改服务端的上下文长度，只记录它 | 本地推理服务超出上下文时静默截断，表现为「模型不理工具」，并且会污染工具调用基准的数据 | 设计评估第 2 点 |
| D-310 | 工具调用路径实现为内部的拦截链，v0.3 固定三环：参数校验、审批、执行。不导出，不提供注册接口 | 审批是这条链的第一个真实用例；v0.4 的内核整形和 v0.6 的中间件在它上面扩展，不必推倒重写 | 设计评估第 3 点 |
| D-311 | `trace.to_json` 从 v0.8 提前到 v0.3，并增加 `GOLE_TRACE_DIR` 自动落盘；run 失败时轨迹挂在异常的 `trace` 属性上 | 审核和开发现在是同一方，项目负责人的本机 live 验收是唯一独立的环节；验收失败时要能把轨迹文件直接发回来 | 设计评估第 6 点 |
| D-312 | 降级解析用语料测试：样本来自基准和 live 里真实出现的坏输出，数量不受测试纪律的上限约束 | 两次审核的「必须」问题都靠审核方的一次性脚本才发现；降级解析是核心卖点，值得长期保留的回归样本 | 设计评估第 5 点 |

| 编号 | 决策 | 理由 | 来源 |
| --- | --- | --- | --- |
| D-010 | 模式 C 的承诺（D-001）保持不变，但在 v0.4 定稿协议测试之前，先做一次一到两天的抛弃式验证：把一个带工具的 Agent 和一个两步流程手工映射到 LangGraph，逐项检查原生内核已有的语义能否对应。产出一页结论，代码不合入 | `Engine` 协议到 v0.7 才设计，而 v0.1 到 v0.3 每版都在增加只有原生内核才有的语义；到 v0.7 才发现映射不上，代价最大 | 设计评估第 1 点 |
| D-011 | v0.4 增加一张内核整形任务卡：运行循环改成可序列化、可逐步推进的 `Run`，模型调用和工具调用经过同一条拦截链；对外行为不变 | `kernel/engine.py` 的 `_actions` 已经承载输出纠正、降级、知识注入和 token 缓冲；v0.5 的断点恢复、v0.6 的中间件与手动驱动、v0.7 的引擎都需要把它打开，集中做一次比三次各改一遍便宜 | 设计评估第 3 点 |

| D-013 | PR 的 CI 增加 `windows-latest`（Python 3.11）；测试纪律对降级解析的语料测试破例（见 D-312 和 DEV_GUIDE §4.1） | 项目负责人的验收机是 Windows，v0.3 起有终止进程树这类平台相关代码；Windows 上的问题应当在 PR 阶段暴露 | 设计评估第 5 点 |
