## 2. 做得好的地方

- **流程**：一卡一提交，标题带任务编号并有正文；评审的 9 条必须修改项一条一个提交，可以逐条追溯。v0.1 审核提出的日志要求全部落实。

## 3. 问题清单（R1–R7 转入 v0.3 任务书 P0）

| 编号 | 级别 | 问题 | 位置 | 修复要求 |
| --- | --- | --- | --- | --- |
| R1 | 必须 | 原生模式下只要注册了工具，流式输出就整段缓冲：模型生成完才一次性补发全部 token。探测：每片延迟 0.05 秒的假模型，无工具时首个 token 0.05 秒到达，注册一个工具后首个 token 0.96 秒到达，等于总耗时。`gole chat` 带工具、`knowledge_mode="tool"` 的问答都受影响。原因是 v0.1 审核 R2 要求「拼接全部 token == result.text」，原生模式下只有等流结束才知道这段文本后面有没有工具调用 | `kernel/engine.py` 的 `_actions`、`kernel/evaluator.py` | 按 D-301 放宽不变量：原生模式下内置范式的文本增量到达即发；保证「最后一个 `tool_result` 事件之后发出的 token 拼接 == result.text」（没有工具调用时即全部 token）。`gole chat` 在中间文本和后续输出之间换行。prompt 模式和指定 `output=` 时的行为不变 |
| R2 | 必须 | 长期记忆的事实抽取失败会让已经完成的 run 失败。探测：`memory=LongTerm()`，回答已生成（流式下 token 已全部发出），抽取调用抛 `ModelError`，`agent.run` 随之抛错，调用方拿不到 `Result`。`Summary` 压缩失败只记 warning，两者不一致。本地小模型上抽取超时或断连并不少见 | `kernel/engine.py` 的 `execute`、`memory/longterm.py` 的 `save` | 按 D-302：`memory.save` 抛出的异常（包括保存阶段触发的 run 超时）不再使 run 失败。引擎记 warning，发一个 `recoverable=True` 的 `error` 事件，不发 `memory_save`，照常返回 `Result`。`Layered.save` 仍然等两层都结束再上报第一个异常 |
