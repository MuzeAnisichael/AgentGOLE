协议层（`golekit.protocols`）：

```python
class Capabilities(BaseModel):
    tools: bool = False
    json_mode: bool = False
    vision: bool = False
    json_schema: bool = False                  # 新增
    context: int | None = None

class CallModel(BaseModel):
    messages: list[Message] | None = None
    use_tools: bool = True
    emit_tokens_after: str | None = None
    model: ModelClient | None = None           # 新增：这一次调用改用别的模型
    visible: bool = True                       # 新增：False 时不发 token
    response_schema: dict[str, Any] | None = None   # 新增

@runtime_checkable
class Approver(Protocol):
    async def approve(self, tool: str, args: dict[str, Any]) -> bool: ...

class StepContext(BaseModel):                  # 新增 4 个字段
    downgrade: Callable[..., None]             # downgrade() 或 downgrade("json_schema")
    approver: Approver | None = None
    capabilities: Callable[[], Awaitable[Capabilities]] | None = None
    constrained: bool = False

class Trace:
    def to_json(self, path: str | Path | None = None) -> str: ...
```

其他对外可见的变化：

- 事件：新增 `approval_required`；`model_end` 增加 `context_used`（提示词占上下文长度的比例，长度未知时为 `None`）。
- 异常：新增 `UnsupportedSchemaError(ModelError)`；运行失败时异常带 `trace` 属性。
- 环境变量：`GOLE_TRACE_DIR`、`GOLE_CONTEXT`、`GOLE_SEARCH_PROVIDER`、`TAVILY_API_KEY`。
- `gole.yaml`：新增 `providers.<name>.context` 和 `tools.<name>.provider`。
- 工具对象可以选择实现 `check_arguments(arguments)` 和 `confirm` 属性；`Tool` 协议本身没有变，不实现的自定义工具照常工作。
- `gole doctor` 每行多了「约束解码」和「上下文」两栏；`gole chat` 在没有配置审批时默认使用 `Console()`。

## 4. 偏差与决策

| 决策 | 原因 | 影响范围 | 需要审核方确认吗 |
| --- | --- | --- | --- |
| 范式通过延迟导入公共的 `Model` 来解析模型字符串和别名，并用 `primary_model` 属性告诉 Agent 主模型 | 任务书要求 planner/executor/critic 接受 spec 和别名，而 D-212 限制 `paradigms/` 的依赖方向；只有 `Model` 知道别名和配置 | `paradigms/_shared.py`、`agent.py` | 是 |
| HTTP 400 和 422 都触发去掉 `response_format` 重发；只有重发成功才把模型标记为不支持 | 部分服务端用 422 表示请求体校验失败；重发也失败说明问题不在 schema，不应降级 | `models/client.py`、`kernel/evaluator.py` | 是 |
| R4 让已删除的显式来源在检索时抛 `ConfigError` | R4 的字面要求；但它和 R10（来源变动后的增量行为）有交互，长期运行的 Agent 会因为一个文件被删而失败 | `knowledge/loaders.py` | 是 |
| 引擎在发出一步的 `step` 事件之前，先向范式要下一个动作 | `thought` 是范式解析上一步回复后才知道的，要标注在产生它的那一步上 | `kernel/engine.py` | 否 |
| `visible=False` 的调用走非流式的 `generate`；`Finish` 时已发出的 token 不是最终输出的前缀则抛 `ModelError` | 不可见的调用没有消费流的必要；不一致说明范式漏标了中间调用，尽早暴露 | `kernel/` | 否 |
| `StepContext` 比任务书多了 `capabilities`、`constrained`，`downgrade` 带一个 feature 参数；`Approver` 加了 `runtime_checkable` | 范式要知道能否使用约束协议；pydantic 校验协议类型字段需要运行时可检查 | `protocols/` | 否 |
| 受约束的工具协议用 `enum: [name]` 而不是 `const`，把 `$defs` 提到顶层；有工具名为 `final_answer` 时退回文本协议 | `enum` 的服务端兼容性更好；嵌套的 `$defs` 引用会失效；`final_answer` 是协议保留名 | `paradigms/react.py` | 否 |
| 约束协议选出 `final_answer` 后，另发一次不带协议的普通调用来写回答 | 让最终回答可以流式输出，文本不夹在 JSON 里 | 每次受约束的运行多一次模型调用 | 否 |
| 计划、检查、汇总调用看到完整的原始对话，只替换最后一条用户消息；执行每一步时只带开头的 system 消息和一条用户消息，前几步的结果截到 2000 字符 | 控制小模型的上下文占用 | `paradigms/plan.py` | 否 |
| 范式内部的提示词用中文；`Reflect` 的默认标准是「回答准确、完整、切题」 | 项目的默认使用语言 | `paradigms/` | 否 |
| `python`、`shell` 在工具线程里用阻塞的 `Popen`，超时后杀掉整个进程树 | asyncio 的子进程在 Windows 的部分事件循环上不可用 | `tools/system.py` | 否 |
| `files` 拒绝所有绝对路径，包括落在 root 内的 | 规则简单，模型不需要知道 root 的真实位置 | `tools/files.py` | 否 |
| `web_fetch` 拒绝所有非公网地址（私有、回环、链路本地、保留段），并接受 `application/xhtml+xml` | 比「私有地址」更严，覆盖云元数据地址 | `tools/web.py` | 否 |
| 联网工具的测试通过私有构造函数 `_search_tool`、`_fetch_tool` 注入 `MockTransport` | 不想在公共签名上加只为测试用的参数 | `tools/web.py` | 否 |
| 每次运行开始时都解析模型能力，显式设置了 `tool_mode` 时也一样；独立的 planner、critic 每次运行各探测一次 | 约束解码和上下文告警都依赖能力。经 `Model` 创建的主模型按进程缓存，对 Ollama 是每个进程一个 `/api/show` 请求 | `kernel/evaluator.py` | 否 |

## 6. 测试概况

- 单元测试：177 个通过，13 个 live 被排除；`make check` 全部通过。v0.2 结束时是 108 个。
- live 测试：待人工验证，5 项，一次都没有运行过。
- 跳过的测试：`files` 的符号链接断言在 Windows 上不执行。没有 `xfail`。
- PR #5 的 CI 在 `29d925f` 上通过：Ubuntu 和 Windows，Python 3.11。`python`、`shell` 的子进程测试因此在 Windows 上跑过一遍。
- **没有测试覆盖的风险点**：
  - Ollama、LM Studio、vLLM、OpenAI 是否接受我们发出的 `response_format`，尤其是带 `anyOf` 和顶层数组的 schema。
  - DuckDuckGo 真实页面的结构是否与手写样本一致，以及它对自动请求的限流。
  - `python`、`shell` 在 Windows 真实终端里的输出编码（CI 只覆盖了 ASCII 和超时终止）。
  - `Console` 在真实终端里与 `gole chat` 的输入提示交替时的显示效果。
  - `plan`、`reflect` 在真实小模型上的效果：计划能否解析、检查是否过于频繁地要求重规划。

## 7. 已知问题与技术债

| 问题 | 现象 | 已尝试的方案 | 怀疑的原因 | 建议 |
| --- | --- | --- | --- | --- |
| DuckDuckGo 解析基于手写样本 | 真实页面结构不同时，`web_search` 返回空结果 | 按公开的 HTML 版页面的类名写了解析器 | 开发环境不能访问真实页面 | C11 的联网项会暴露；失败时把轨迹发回 |
| OpenAI 的 strict 模式可能拒绝部分 schema | 顶层数组或 `anyOf` 被 400 拒绝，然后回退到无约束 | 回退路径有测试 | strict 模式对 schema 形状有额外限制 | 实测后决定是否对 OpenAI 默认关闭 |
| `verbose` 的实时轨迹把 plan、reflect 的连续模型调用标成「重新调用」 | 显示上有误导，不影响结果 | 无 | `LiveTrace` 只认识 ReAct 的节奏 | v0.4 让范式给调用起名 |
| 语料全部来自单元测试 | 不代表真实模型的失败分布 | 无 | 没有实测数据 | C12 之后补 |
| `docs/` 没有同步 | SPEC 没有写可选的 `check_arguments`、`StepContext` 新字段、新的 `gole.yaml` 键和环境变量 | 开发方不能改 `docs/` | — | 审核时更新 SPEC |

| --- | --- | --- | --- |
| 单个 agent（兼 Lead 与三个 Builder） | R1–R7、T1–T11、P3、P4 | 全部 | 无冲突。T2 的提交曾带着一个测试里的 pyright 错误，推送前已修正并合进原提交 |

- 接口变更次数：2。`StepContext` 在 T6 增加 `capabilities`、`constrained` 并给 `downgrade` 加了参数；`Approver` 在 T3 加了 `runtime_checkable`。
- Reviewer：**没有独立的评审者**。P3 是开发者自查，发现并修了 3 处（RV1 临时目录清理失败、RV2 direct 检查时记忆工具缺 session、RV3 基准读取 Ollama 地址）。自查不能替代独立评审，这一点请审核时考虑。
